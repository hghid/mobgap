## Desktop application goal

- Develop an installable Electron application that runs the Python movement and accelerometer processing code in `src/mobgap/` through Pyodide (CPython compiled to WebAssembly). End users must not need Python, pip, Conda, a compiler, or a separately installed processing service.
- Target Windows, macOS, and Linux with the same Python algorithms and application source. Electron installers remain specific to the operating system and CPU architecture. Define supported OS versions and architectures explicitly, and verify each target before claiming support; “100% cross platform” is a goal, not an established property of the current repository.
- Preserve the published Python package, scientific behavior, and native Python workflows under `.agents/refactor-policy.md`. Keep Electron code, JavaScript dependencies, and build configuration in a dedicated application directory such as `desktop/` when introduced. Keep scientific processing in Python behind a small adapter rather than duplicating algorithms in JavaScript.
- These are development requirements for the desktop application, not a statement that Electron packaging or Pyodide compatibility already exists.

## Establish Pyodide compatibility first

- Before building out the UI, prove that a wheel built from this repository can be installed, imported, and used for one representative end-to-end processing job in the selected Pyodide runtime. Test the installed wheel and its resources, not imports from a source checkout.
- Audit the full transitive dependency graph against `pyproject.toml`, including Python version requirements and imports triggered by package `__init__.py` files. Record tested versions, supported features, unresolved blockers, and reproducible verification commands beside the application code. Native CPython installation success does not demonstrate WebAssembly compatibility.
- Compiled dependencies require wheels built for the selected Pyodide Python/Emscripten ABI. Desktop wheels for NumPy, SciPy, pandas, scikit-learn, PyWavelets, or other native extensions cannot be reused. Use compatible Pyodide packages and pure Python wheels; verify their versions satisfy package metadata. Do not bypass the resolver with `deps=False` to conceal incompatible requirements. See [Pyodide package loading](https://pyodide.org/en/stable/usage/loading-packages.html).
- Treat Numba as a compatibility blocker until demonstrated otherwise in the pinned runtime. This repository uses `njit`, `guvectorize`, explicit signatures, and `numba.typed.List` across gait detection, filtering, and orientation utilities. `NUMBA_DISABLE_JIT=1` alone does not remove the dependency or establish equivalent behavior. Prefer explicit, tested Python/NumPy implementations behind a narrow compatibility layer where needed; avoid global fake modules, broad monkey patches, and silent algorithm substitutions.
- Audit the optional Rust extension `cwa-reader-rs` used by AX6/CWA and weartime features separately. Supporting these inputs requires a compatible WebAssembly implementation and decoding parity tests. Surface unsupported formats clearly rather than silently omitting them or introducing an unapproved native Python fallback.
- Start with serial Python execution (`n_jobs=1` where applicable). Audit joblib/tpcp paths and transitive thread/process use; do not depend on subprocesses, multiprocessing, or Python threads in the baseline runtime. A JavaScript Web Worker keeps the UI responsive but does not enable Python multiprocessing. See [Pyodide compatibility constraints](https://pyodide.org/en/stable/usage/wasm-constraints.html).
- Any dependency split, optional import, or fallback must preserve the existing public Python API and native behavior. Apply the repository-local tpcp skills when modifying algorithms, pipelines, datasets, or their parallel execution.

## Runtime architecture and Electron boundaries

- Run Pyodide and processing jobs in a dedicated Web Worker, away from both the renderer UI thread and Electron's main process. Use the worker module format supported by the pinned runtime. Initialize once, await readiness, and serialize jobs within each interpreter. `runPythonAsync` on the UI thread does not make CPU-bound Python work nonblocking. See [Pyodide workers](https://pyodide.org/en/stable/usage/webworker.html).
- Keep native dialogs and host filesystem access in Electron's main process, a small `contextBridge` API in preload, UI rendering in the renderer, and Python execution in the worker. Keep `nodeIntegration: false`, `nodeIntegrationInWorker: false`, `contextIsolation: true`, `sandbox: true`, and `webSecurity: true`.
- Expose named operations with validated arguments and results. Validate IPC senders and enforce access to user-selected files in the main process; never expose arbitrary filesystem access, raw `ipcRenderer`, shell commands, or Python source execution through the bridge. Pass data to fixed Python entry points without interpolating filenames or user input into executable Python strings.
- Load bundled content through a restricted custom application protocol with the privileges needed for local workers and resource loading. Constrain protocol paths to packaged assets, reject traversal, return correct MIME types, and test WebAssembly loading in the installed app. Use a restrictive CSP with only the WebAssembly permissions required by the pinned engine; do not disable CSP or Electron security to make loading work. Block unexpected navigation and window creation. Follow [Electron security guidance](https://www.electronjs.org/docs/latest/tutorial/security).
- Define a versioned message contract with request IDs, input metadata, progress, results, and structured errors. Include cancellation, timeouts, worker failure recovery, and cleanup. A busy worker cannot handle a cancellation message during synchronous Python computation: provide termination and recreation as a reliable fallback. If using Pyodide interrupt buffers, verify SharedArrayBuffer and isolation requirements in the packaged app.
- Transfer large recordings as typed arrays or binary buffers with explicit dtype, shape, channel order, and ownership. Avoid JSON encoding entire recordings and repeated full-size copies. Convert results to transferable or serializable values and release owned `PyProxy` objects and buffer views in `finally` blocks. See [Pyodide type translations](https://pyodide.org/en/stable/usage/type-conversions.html).

## Scientific data and local files

- Validate sampling rate, units, sensor/body coordinate frame, axis names, timestamps, missing values, and required channels at the adapter boundary. Use the existing MobGap contracts; do not guess whether acceleration is in g or m/s². Some algorithms require gyroscope data or participant metadata, so an accelerometer-only input must not be presented as sufficient for every pipeline.
- Preserve sample indexing, interval boundaries, floating-point precision, preprocessing, and result schemas. Include algorithm parameters, package/runtime versions, sampling rate, units, and input provenance with exported results so a run can be reproduced.
- Treat Pyodide's virtual filesystem as separate from the host filesystem. Import only selected input bytes, use job-specific temporary paths, export through the main process, and delete temporary data after completion or cancellation. Persist settings and caches in Electron's per-user application directories, never the installation directory. See [Pyodide filesystem behavior](https://pyodide.org/en/stable/usage/file-system.html).
- Set input-size and memory limits and report actionable errors. Benchmark representative long recordings, including JavaScript/Python transfer overhead and peak memory. Chunk only where algorithm state, filter boundaries, overlapping windows, and global indexing are preserved and validated against whole-recording results.
- Keep movement data local by default. Do not upload recordings or include raw signals, participant identifiers, or sensitive paths in logs, telemetry, or crash reports. Load only trusted bundled models; never unpickle user-supplied files with joblib/pickle. Verify the bundled Ullrich models and their scikit-learn compatibility.

## Reproducible, offline packaging

- Pin Electron, Pyodide, the JavaScript toolchain, and the complete desktop Python dependency set with lockfiles and integrity hashes. Maintain a desktop runtime manifest alongside the existing native `uv.lock`; the native lockfile alone does not describe the WebAssembly environment. Verify compatibility with Electron's bundled Chromium when upgrading either runtime.
- Bundle the Pyodide loader, WebAssembly binary, standard library, package lock metadata, every required wheel, and MobGap resources/models from the same tested runtime set. Point the loader and package URLs at packaged assets. Do not fetch code or dependencies from a CDN/PyPI at startup or first use. See [Pyodide deployment guidance](https://pyodide.org/en/stable/usage/downloading-and-deploying.html).
- Build the MobGap wheel using the existing `pyproject.toml` build configuration. Do not maintain a copied Python source tree for the app. Include required resources in the wheel and verify access after installation. Replace runtime example-data downloads through pooch with bundled, redistributable fixtures for demos; keep private evaluation data out of installers.
- Use one maintained Electron packaging tool, preferring Electron Forge for a new application unless existing application tooling dictates otherwise. Resolve assets from packaged application resources rather than the working directory. Verify worker, wheel, model, and WebAssembly paths with ASAR enabled; unpack only resources that actually require it. See [Electron packaging](https://www.electronjs.org/docs/latest/tutorial/application-distribution).
- Produce and test separate artifacts for every supported OS/architecture using appropriate build runners. Include dependency licenses/notices, Windows signing, and macOS signing/notarization in release preparation. Keep signing credentials outside the repository. Package application code and its Python runtime/dependencies as a tested unit for releases and updates.
- Document actual setup, development, build, packaging, and verification commands beside the app once implemented. Distinguish required build-time tools from the self-contained end-user runtime. Do not document commands or supported targets that have not been verified.

## Verification required for desktop changes

- Keep existing native Python checks passing. The repository currently installs test dependencies with `uv sync --locked --no-dev --group test`; run relevant tests with `uv run --no-sync pytest <test-path>`. Use targeted tests during development and the established CI checks before merging runtime or algorithm changes.
- Compare native CPython and the pinned Pyodide runtime on the same fixtures and parameters. Check event indices, interval boundaries, labels, numerical outputs, and schemas with justified tolerances. Include empty/short inputs, malformed data, missing channels, supported sampling rates, and realistic long recordings. Never rewrite expected scientific results merely to accommodate a port.
- Add tests in the actual Electron worker/runtime as well as Python unit tests. Cover initialization failure, unsupported dependencies/formats, import-process-export, repeated runs, cancellation, worker restart, and resource cleanup.
- Smoke-test installed release artifacts on Windows, macOS, and Linux for each advertised architecture, on machines without Python and with network access disabled from first launch. Verify asset loading, processing, saving/reopening results, paths containing spaces and Unicode, read-only installation directories, and OS-specific file dialogs. A development-server run or native Python CI pass is insufficient evidence of desktop support.
- Report checks actually run, numerical/performance findings, and remaining platform or feature limitations. Do not claim universal compatibility, offline readiness, or successful packaging without evidence from the corresponding artifacts.
